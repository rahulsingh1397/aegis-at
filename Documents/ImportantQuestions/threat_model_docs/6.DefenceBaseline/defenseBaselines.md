# §6 — Defense Baselines: Working Notes

## Locked decisions

- Four baselines, config flags over ONE codebase, each adds one layer.
- Per-baseline spec is "signal read" + "tracks executor?":
  - B1 shared account → shared identity → attribution UNDEFINED → AIS ~0
  - B2 per-agent identity → execution-time authenticator → tracks
       executor → AIS ~1.0  ← gets it RIGHT
  - B3 + RFC 8693 act claims → current actor (top-level act.sub =
       Enrich, requester) → does NOT track executor → AIS ~0  ← THE DROP
  - B4 + tamper-evident log → same signal as B3, integrity only →
       AIS ~0
- Curve is NON-MONOTONIC. Rises B1→B2, falls at B3, flat at B4.
- Headline = the drop at B3.

## The headline finding, stated tightly

Per-agent identity binds attribution to AUTHENTICATION (executor).
RFC 8693 binds attribution to the delegation chain's CURRENT ACTOR
(requester), as MANDATED by §4.1 (MUST consider current actor, MUST
NOT use prior actors for access decisions). They diverge when
requester != executor (Path B). Adding the standard non-repudiation
primitive REGRESSES attribution — by following the standard
correctly, not by violating it.

## RFC 8693 spec-compliance corrections (after reading the actual RFC)

- Token structure: sub = PRINCIPAL (analyst), act.sub = CURRENT ACTOR
  (Enrich), nested act = prior actor (orchestrator). Per RFC 8693
  §4.1 and Appendix A.2.5. Contain (executor) appears NOWHERE in the
  token. Earlier drafts had sub = Contain — that was NON-COMPLIANT.
- The finding's strongest form: §4.1 MANDATES attributing to the
  current actor and FORBIDS using prior actors for access decisions.
  Spec assumes current-actor == wielder (§A.2.3). Path B violates
  that. No spec-compliant field records the executor. Misattribution
  is mandated by the standard, not chosen by implementation.
- Correct citations: act claim = §4.1; scope = §4.2; may_act = §4.4;
  delegation example = Appendix A.2.5; exchange request = §2.1.

## Baseline 2 = 1.0 — the load-bearing assumption (and its defense)

B2 = 1.0 rests on: attribution at authentication time tracks the
executor, because the executor (Contain) is who authenticates at the
tool. This is the basis of the entire non-monotonic story and the
single most attackable point.

§9 defense — the hardest objection:
Reviewer: "In B2, how does Contain hold authority for a containment
action it didn't request? Doesn't authority flow from Enrich?"
Answer: In B2, AUTHORIZATION still flows through Enrich's request,
but ATTRIBUTION is determined separately at authentication time by
whose credential executes (Contain). B2 separates "who was
authorized" from "who is recorded acting." RFC 8693's innovation is
to BIND these in the token — and that binding carries the requester's
identity into attribution, which is the regression.

## §4 consistency note (principal_chain redundancy)

In Path B, claimed_principal_chain = [enrich, orchestrator, analyst],
true_principal_chain = [contain, orchestrator, analyst]. They differ
only in the first element — the same info the actor field captures.
So actor-defect and chain-defect are CORRELATED for this attack.
Accepted as (a): honest, disclosed in §6 Hypotheses subsection, and
the defect-breakdown metric will show they flag together. Not a flaw;
it's a true property of the attack. Do NOT redefine the chain to
manufacture independence.

## §9 hooks generated by §6

- B3 "mandated by §4.1" framing is the answer to "isn't this just a
  logic bug / implementation choice?" — no, it's required by the RFC.
- B4 negative result was PRE-DECLARED in §2 Boundary 4. Predicted-
  then-confirmed > surprising the reviewer. Reference Boundary 4.
- NIST/NCCoE Feb 2026 emphasizes BOTH primitives (signed delegation,
  tamper-evident logs) for non-repudiation. The benchmark shows
  neither closes the gap. This is the policy-relevant punchline.

## may_act (RFC 8693 §4.4) — deferred

Other tool raised may_act. It governs AUTHORIZATION to act, not
attribution. Contain is legitimately authorized, so may_act doesn't
prevent the attack. Candidate defense-in-depth note or backlog item,
NOT part of the core mechanism. Mention in §7 backlog or §9 at most.

## Cross-check history (for the record)

The non-monotonic curve was first surfaced by the other tool. Its
initial mechanism ("innermost act.sub = Enrich") was WRONG — innermost
is the least-recent actor (orchestrator), not Enrich. Corrected
against RFC 8693 §4.1 to "current actor / outermost / top-level
act.sub = Enrich." The sub=Contain token shape was also non-compliant,
corrected to sub=principal against Appendix A.2.5. Both corrections
came from reading the actual RFC, not from either tool's paraphrase.
