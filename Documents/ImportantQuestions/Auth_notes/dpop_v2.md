## What DPoP is and why it closes the gap

DPoP (RFC 9449, "Demonstrating Proof-of-Possession") binds a token to a
key the holder must prove possession of *on every request*. The token
carries `cnf: {"jkt": <thumbprint>}` (RFC 7800 confirmation claim); the
holder presents a freshly-signed **proof JWT** alongside it; the resource
checks that the proof's key matches the token's `cnf.jkt`.

Why this closes the v1 gap (§5.2): under B1–B4, the token minted naming
Enrich is an **unbound bearer** — Contain can lift it and present it, and
nothing detects the substitution. That lift is the entire attack. Under
B5 the token's `cnf.jkt` is *Enrich's* thumbprint; Contain cannot produce
a proof under Enrich's private key, so the lift is rejected at the tool.
To act legitimately, Contain must obtain its **own** token — bound to
Contain's key, naming Contain as current actor. The claimed actor then
tracks the executor, and AIS recovers.

The mechanism is symmetric at both endpoints: the **orchestrator's** token
endpoint also requires a proof before it binds a new token (you cannot get
a token bound to a key you do not hold), and the **tool** requires a proof
before it honors a bound token. A lift is rejected at the tool; a
fraudulent bind is rejected at the orchestrator.

## Locked decisions

### Ed25519, not RSA

`DPoPKey` wraps an `Ed25519PrivateKey` (dpop.py:110). RFC 9449 permits any
JOSE asymmetric algorithm; Ed25519 gives compact, deterministic
signatures and fast keygen — and crucially it makes `dpop.py` a **leaf
module** that does not pull in `auth.tokens` (which generates a 2048-bit
RSA key at import). That leaf property is what lets `dpop_executor_body`
import `dpop` inside an agent subprocess cheaply (see `agent_proc_v2.md`,
leaf-module discipline). The signing/verification key for *tokens* is
still RSA in `tokens.py`; DPoP keys are a separate, per-agent Ed25519
keyset.

### Keys cross the process boundary as PEM, not as objects

`DPoPKey.from_private_pem` / `.private_pem` (dpop.py:116–135). The
`Ed25519PrivateKey` object holds a non-picklable handle, so it cannot be a
`spawn` argument. The harness provisions an agent's key by shipping PKCS8
PEM **bytes** as a spawn arg; the agent rebuilds the key in its own
process (`dpop_executor_body`). The bytes are provisioned BEFORE the
agent's user code runs, so the §3 adversary (alert text only) never
touches them. Precise provenance (threat-model-v2.1 §A5): the keypair is
**harness-generated** and handed to the agent — it is not generated by the
agent — but the private half is then used **only inside the agent process**
to sign the call-time proof, and only signed proofs cross back over the IPC
boundary. The security-relevant invariant is the outbound one: the private
key never leaves the agent process once provisioned; the tool sees public
material only.

### Thumbprint is RFC 7638 canonical (order-independent)

`jkt_thumbprint` (dpop.py:93–102) hashes only the REQUIRED JWK members
(`crv`, `kty`, `x`) in lexicographic order with tight separators. This is
what makes a `jkt` reproducible regardless of dict ordering — the same key
always yields the same thumbprint on both the mint side and the verify
side. Verified against RFC 7638's construction, not assumed (INV-8).

### Proofs are endpoint-scoped (htm/htu)

`RESOURCE_HTU` (the tool) and `TOKEN_ENDPOINT_HTU` (the orchestrator's
mint endpoint) are distinct (dpop.py:51–53). A proof minted for the tool
will not satisfy the orchestrator and vice versa — RFC 9449's htm/htu
binding scopes a proof to exactly one method+endpoint. This prevents a
proof captured at one endpoint from being replayed at another. These
constants live in the leaf module so subprocesses can import them without
the RSA cost.

### Replay cache is harness-held, single-use jti

`ReplayCache` (dpop.py:170–181) lives in the parent harness process — no
agent or the orchestrator holds it, the same isolation pattern as the
ground-truth recorder and the tamper-evident logger key. A `jti` seen
twice is a `ProofReplayError` (§5.4). v2's cache is an unbounded set
(deterministic test runs are short); a production cache would bound it to
the proof window TTL — named, not built.

### Verification order is fixed and fail-loud

`verify_proof` (dpop.py:184–249) runs, in order: (1) signature under the
proof's *embedded* JWK, (2) htm/htu match, (3) `jkt(proof) == bound_jkt`,
(4) `iat` within ±`window_s`, (5) jti not seen (then record it). Each
failure raises a distinct `DPoPError` subclass (`ProofSignatureError`,
`ProofBindingError`, `ProofReplayError`, `ProofStaleError`) so a test can
assert *which* check fired (Rule 9 — tests verify intent, not just that
*something* was rejected). The proof is self-attesting: the embedded JWK
proves possession; the `cnf` binding is what ties that possession to the
granted token.

## What B5 requires elsewhere (the surface this primitive touches)

DPoP is one new module plus small, optional hooks in three existing files
— each gated so the B1–B4 path is byte-for-byte the v1 path:

- `tokens.py exchange_token(..., cnf=None)` — adds `cnf:{jkt}` to claims
  only when set. See `tokens.md`.
- `orchestrator.py mint_delegated_token(..., cnf=, proof=, replay_cache=)`
  — requires + verifies a proof before binding. See
  `orchestrator_notes.md`.
- `siem_action(..., proof=, replay_cache=)` — if the verified token
  carries `cnf`, requires + verifies a proof before resolving identity.
  See `siem_action.md`.

Every one of those is `None`/absent on B1–B4, so INV-6 holds: B5 differs
from B3/B4 by a flag, not a fork.

## INV walkthrough

- **INV-1 (token structure):** ✓ — `cnf` is an RFC 7800 confirmation
  claim, orthogonal to the `sub`/`act` structure; it binds the token to a
  key, it does not name an actor. The actor is still `act.sub`.
- **INV-2 (current actor resolution):** ✓ and load-bearing — B5's point
  is that the executor must obtain a token whose `act.sub` IS the
  executor; DPoP forces that by rejecting the lift. Identity is still read
  from `act.sub`, never from the proof.
- **INV-3 (siem_action naming):** ✓ — the tool is unchanged in name.
- **INV-4 (ground-truth independence):** ✓ — the proof is an
  agent-supplied field; it is verified by the tool but NEVER read by the
  recorder for identity. The recorder still uses the kernel PID.
- **INV-5 (no illegitimate behavior):** ✓ — the §5.2 lift is a
  harness-constructed credential/key mispairing, not agent misconduct.
- **INV-6 (baselines as config flags):** ✓ — see surface section above.
- **INV-7 (pre-registered):** B5 AIS = 1.0 (§5.3) and the replay/stale
  rejections (§5.4) are locked before this code measured anything.
- **INV-8 (verify against source):** ✓ — RFC 7638 thumbprint, RFC 9449
  htm/htu binding, and RFC 7800 cnf shape were each checked against the
  spec; exercised in `tests/test_baseline5_dpop.py`.
